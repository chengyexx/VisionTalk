# Vision Talk — 设计文档

## 一、项目概述

Vision Talk 是一款 AI 视觉对话助手。用户打开摄像头与麦克风，AI 能够实时看到画面、听到语音，并以语音做出自然回应。核心设计理念是「重边缘预处理 + 异步流式编排」——在客户端完成尽可能多的工作，仅将关键信息送向云端。

---

## 二、用户故事：计划 vs 实际

### 计划的用户故事

| # | 故事 | 场景 | 技术要点 |
|---|------|------|----------|
| **A** | 桌面级硬件调试助手 | 用户将摄像头对准开发板/路由器，询问"这个跳线接得对吗？""板子上的报错灯是什么意思？" | 高精度视觉识别、领域知识 |
| **B** | 环境探索与物体问答 | 用户举起陌生商品/书籍，问"这是什么？有什么用？" | 通用视觉识别、百科知识 |
| **C** | 实时动作/情绪陪伴 | AI 持续观察用户面部表情，打哈欠时主动提醒"看起来你累了，要听音乐吗？" | 高帧率持续分析、情感识别 |

### 最终实现的用户故事

| # | 实现状态 | 实现方式 |
|---|----------|----------|
| **A** | ✅ 已实现 | VAD 触发 → 抓帧 → VLM 多模态推理。摄像头对准硬件时 AI 能看到并回答。覆盖"这是什么板子"到"灯为什么闪"的全谱问题。 |
| **B** | ✅ 已实现 | 同管线。VLM 模型本身具备通用物体识别能力，DeepSeek/ChatGPT 均可胜任。 |
| **C** | ❌ 未实现 | 见下方分析。 |

### 故事 C 为何放弃（工程思考）

故事 C 要求持续 24fps 视频流送云端做情感分析，会带来三个致命问题：

1. **成本爆炸**：单次对话 30 秒 × 24fps = 720 帧图片。每帧 500-800 token，单次消耗 36 万-58 万 token。按 DeepSeek 视觉模型定价，一次对话成本可达数元，无法规模化。

2. **网络拥塞**：持续传输视频流占用大量带宽，导致语音交互延迟飙升，破坏核心体验。

3. **违背架构初衷**：本项目核心设计是"视觉休眠 → 事件触发"，故事 C 要求持续监控，与端云协同成本控制策略直接冲突。

**启示**：不是所有看似"酷"的功能都适合上。工程决策的本质是知道什么不做。

## 三、成本控制策略：思考 vs 采用

### 策略 1：降低图像分辨率

| 阶段 | 描述 |
|------|------|
| **脑暴** | 将所有上传图像压缩至 360p 或更低 |
| **实际** | ❌ 未采用 |

**原因**：降低分辨率会直接损害 VLM 的视觉理解准确度。对于硬件调试场景（故事 A），用户需要看清板子上的小元件和丝印，低分辨率会导致误判。**用准确度换成本是本末倒置**。

### 策略 2：本地部署小模型意图拦截

| 阶段 | 描述 |
|------|------|
| **脑暴** | 本地跑极小的语言模型，判断用户指令是否需要调用视觉（如"今天天气怎么样"就不传图） |
| **实际** | ❌ 未采用 |

**原因**：在浏览器端运行另一个模型增加复杂度和首屏加载时间。且 VAD 本身已经是有效的"意图拦截器"——不说话 = 不传任何数据。加上额外模型是过度工程。

### 策略 3：事件驱动的按需抽帧 ✅

| 阶段 | 描述 |
|------|------|
| **脑暴** | 放弃持续分析，仅在用户发声的瞬间抓一张图片上传 |
| **实际** | ✅ **已采用** — ROI 最高的策略 |

**具体实现**：系统平时处于「视觉休眠」状态。只有当 VAD 检测到用户开始说话，且本地帧差分算法计算出当前画面与上次上传的画面有显著差异时，才将最新图像作为 payload 发送。**将持续的视频流 Token 消耗降维为单张图像的 Token 消耗。**

**额外优化**：帧差分使用 64×64 缩略图比较，仅需几毫秒。差异像素超过 5% 才触发上传，避免用户轻微晃动导致重复传输。

### 策略 4：上下文视觉缓存

| 阶段 | 描述 |
|------|------|
| **脑暴** | 云端保留上一轮对话的图像特征，通过向量比对决定是否重新分析 |
| **实际** | ❌ 未采用 |

**原因**：需要维护向量数据库，增加运维复杂度。我们用更简单的方案达到了类似效果——

### 策略 5：LangGraph 记忆降维（Token 压缩）✅

| 阶段 | 描述 |
|------|------|
| **脑暴** | 在 LangGraph 状态管理中设置机制：历史对话提取 VLM 生成的文本描述作为长期记忆，舍弃原始图像 |
| **实际** | ✅ **已采用** — 成本控制的点睛之笔 |

**具体实现**：

```
不做降维：
第 1 轮：[图₁ Base64] + "这是什么？"              → ~800 token
第 2 轮：[图₁] [图₂] + "怎么修？"                 → ~1400 token
第 3 轮：[图₁] [图₂] [图₃] + "正常吗？"           → ~2000+ token ← 指数增长

降维后：
第 1 轮：[图₁] + "这是什么？"                      → ~800 token
第 2 轮："画面是一块开发板，红灯闪烁" + [图₂] + "怎么修？" → ~600 token
第 3 轮："画面是示波器显示波形" + [图₃] + "正常吗？"    → ~600 token ← 线性恒定
```

VLM 节点在生成回复后，调用一个廉价的纯文本模型（DeepSeek-Chat，不使用视觉）提取一句话画面摘要。该摘要替换原始 Base64 图片存入对话历史。**确保每次 API 请求最多包含 1 张图片，将多轮对话的成本从指数级压至线性。**

## 四、成本控制策略总结

| 策略 | 脑暴 | 采用 | 理由 |
|------|------|------|------|
| 降低分辨率 | ✓ | ✗ | 损害准确度，得不偿失 |
| 本地意图拦截 | ✓ | ✗ | VAD 已起到等效作用，过度工程 |
| **事件驱动抽帧** | ✓ | **✅** | ROI 最高，流→单帧降维 |
| 云端视觉缓存 | ✓ | ✗ | 运维复杂，可用记忆降维替代 |
| **记忆降维** | ✓ | **✅** | 多轮成本线性化，实现简单 |

**核心思路**：四层漏斗 — 视觉休眠 → 事件触发 → 帧差分去重 → 记忆降维。从原理上把"可能很贵"的视觉对话压缩到可控范围。

## 五、技术架构回顾

```
前端 (React)
├── Camera       — react-webcam, captureFrame()
├── RingBuffer   — FIFO 环形缓冲
├── frameDiff    — 64×64 像素级对比
├── useVAD       — @ricky0123/vad-web, Silero 模型
├── useAudioCapture — MediaRecorder API
├── useWebSocket — 指数退避重连
└── UI           — Cyber-Minimal 暗黑主题

     ↓ WebSocket

后端 (FastAPI)
├── LangGraph 状态机
│   ├── ASR — Whisper / DeepSeek Audio
│   ├── VLM — LiteLLM 多模型, 流式推理
│   └── TTS — OpenAI TTS, 句级流式合成
├── MemorySaver checkpoint
└── 记忆降维 — 图→文摘要
```

## 六、已知局限与后续方向

1. **TTS 延迟**：OpenAI TTS 不支持原生流式，当前用句级分段缓解。后续可评估 DeepSeek TTS 或本地 CosyVoice。
2. **VAD 误触发**：Silero VAD 在嘈杂环境下可能误判。可增加置信度阈值。
3. **多语言**：当前仅支持中文。ASR/TTS 可配置多语言参数。
4. **故事 C 替代方案**：可考虑本地运行轻量表情识别（如 face-api.js），仅将"疲劳"等关键事件通知 AI，避免持续上传。
